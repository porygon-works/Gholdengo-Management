# Gholdengo 家計簿 仕様書（v2）

前の家計簿アーティファクトを置き換える、独立した家計簿Webアプリ。
計算はすべてアプリの計算エンジン（`src/engine/`）で行い、Notion・Claude には依存しない。
見た目と使い方は、今のアーティファクトと同じ感じにする。

---

## 1. 全体の作り

```
Gmail ──(15分ごと)── GAS ──→ Supabase ←──→ Webアプリ（Vercel・PWA）
  三井住友の通知メール        すべての入出金       計算エンジン・画面
```

| 部品 | 役目 |
| --- | --- |
| Webアプリ（Vercel） | 画面と計算。スマホのホーム画面に追加して使う |
| Supabase | すべての入出金・予算・設定を保存。プロジェクト porygon-works（複数のアプリの DB をまとめている）の `ggmg` スキーマに置く。メールでログインし、本人だけが読み書きできる（RLS） |
| GAS（Google Apps Script） | 三井住友カードの通知メールを読み、Supabase に書く。使うのは無料の時間主導トリガーだけ |

Claude は使わない。読めなかったメールはアプリの「要確認」に出す。

---

## 2. 前提

| 項目 | 決定 |
| --- | --- |
| 月の区切り | 暦の月（1日〜月末） |
| 今月の予算 | 給与 ＋ 追加予算 − 固定費 − 目標用マイナス（§5.1）。口座の残高は、足りなくなる日の警告だけに使う |
| 費目予算 | 全費目に予算を持つ。予備は残りが自動で入る |
| カード | 三井住友：月末締め・翌月26日払い（ふだん使う・メールから入る）／セゾン：月末締め・翌月4日払い（家賃とリボ）。どちらも土日祝は翌営業日。カードごとに設定で変えられる |
| 給料日 | 15日（土日祝は翌営業日） |
| 銀行 | 入出金の通知メールはないので、残高はアプリで入れる |
| リボ・分割 | 返済額は「返済」費目の支出。リボで買った物は予算外 |
| 安全残高 | 0円（設定で変えられる） |

## 3. 画面

### 3.1 共通

- **ヘッダー**：画面の名前、表示している月（‹ › で月を移動。ダッシュボード・明細・予定・設定で共通）、ハンバーガーメニュー
  - メニューの中身：残高を入れる・要確認・目標・設定・ログアウト
- **フッター**：画面を切り替えるタブ
  - ダッシュボード・明細・予定・設定

### 3.2 ダッシュボード

1. 表示している月と、月を移動するボタン
2. **今月の予算**（自由に使えるお金 T）と**自由に使える残り**（R）。その下に予算の元（給与・追加予算・固定費・目標用マイナス）と、いまの口座残高・今月これからの引き落とし（残高の報告日より後のもの）・引き落としのあとに残る額
3. **使ったものの入力フォーム**（その場で入れられる）
   - 費目・金額・金種（三井／セゾン／現金／PayPayチャージ／交通系チャージ）
   - 日付は今日が初めから入っている。お店とメモは開いたときだけ入れる
4. **費目ごとの予算と残り**（変動費は1日に使える額も）。変動費・固定費の表それぞれに合計の行
5. **来月の支払い予定**（§5.8）：固定費 ＋ 変動費、リボ・分割があれば足して計
6. **今月の引き落とし**（§5.7）：表示している月に口座から出るお金の表（日・項目・金額・状態）。口座から直接（奨学金・共済など）、カードごとの使った分（前の月の利用から見込み、請求額が分かれば確定。確定したら 請求額 − 返済）、リボ・分割の返済を1行ずつ。最後に合計。カードの行をタップすると請求額を入れられる
7. 要確認の件数（タップで要確認一覧へ）
8. 「口座の見通し」へのボタン（いまの口座残高の枠の中）

### 3.3 明細

- 費目ごとに、使ったものの一覧を見られる（タップで開く）
- 各明細には状態を出す：予定／速報／確定
- 明細をタップすると、費目・金額・メモの直し、立替額の入力、削除（手入力のものだけ）ができる
- 立替額を入れると、返してもらう分を入金の予定として一緒に作れる（日付と受け取り方を選ぶ）。返してもらうまでは立替の分も口座から出たままなので、残り予算はその分少なく出る
- 未分類の明細は一番上にまとめて出す

### 3.4 予定（入出金の予定）

- 給与・賞与・急な入金・大きな出費などの予定を見る。ヘッダーの ‹ › で月ごとに切り替える（入金と出費に分けて出す）
- 今月を見ているときは、日付が過ぎてまだ確定していない予定を一番上に出す
- 予定の追加・直し・**確定にする**（金額を入れて「確定」を押す）
- 定期のお金（§4.4）から作られた予定もここに出る

### 3.5 設定

- **予算**：費目ごとの予算（前の月から引き継ぐ。予備は自動）
- **見込み額**：給与の見込み・賞与の見込み（月と金額）・固定費の見込み
- **定期のお金**：家賃・ローン・保険・通信・サブスクなど（名前・金額・日・金種・費目）
- **資産**：安全残高・目標残高
- **お店→費目のルール**：自動で覚えたものの一覧と直し
- **借金**：リボ・分割の残高と最低返済額

### 3.6 その他（メニューから）

- **要確認**：重複の候補・読めなかったメール・照合できなかった速報
- **目標**：① リボ・分割の残高を0にする ② 引落日に口座が足りない月を0にする ③ 給料日前日の残高を目標以上にする
- **残高を入れる**：口座と現金の今の残高
- **計画をつくる**：リボ返済と、給料日前日に残したい額（手取り1か月分など）までの計画を立てて、各月の目標用マイナスに入れる（5.6）
- アプリの版（Ver・コミット・作った日時）は、メニューのいちばん下・設定→データ・ログイン画面に出す

## 4. データ

### 4.1 すべての入出金は1つのテーブル（`entries`）

予定・速報・確定・手入力・収入・お金の移動まで、すべて `entries` に入れる。

| 項目 | 内容 |
| --- | --- |
| `kind` | 支出／収入／移動（ATM で口座→現金 など） |
| `status` | 予定／速報／確定 |
| `date` | 使った日（予算に数える日） |
| `amount` | 金額（いつもプラスの数で持つ） |
| `method` | クレカ／現金／PayPayチャージ／交通系チャージ／口座／リボ（リボで買った物） |
| `category` | 費目（収入と移動はなし） |
| `shop`・`item`・`memo` | お店・買った物・メモ |
| `tatekae` | 立替額（予算に数えない分） |
| `source` | 手入力／カード速報／カード明細／定期／移行 |
| `source_ref` | 取り込み元のID（メールのID＋何件目か）。同じものを2回入れないためのもの |
| `merged_into` | 重複として吸収された先の明細。吸収されたものは計算に入れない |
| `recurring_id` | 定期のお金から作られたときの元 |
| `not_dup` | 「別のもの」と決めた相手。二度と重複の候補にしない |
| `locked` | 本人が費目などを直した。吸収されても本人の値を残す |

ほかのテーブル：

| テーブル | 中身 |
| --- | --- |
| `balances` | 残高の報告（日付・口座・現金） |
| `card_bills` | カード請求額（引落日・金額）。メールから自動で入る |
| `recurring` | 定期のお金（名前・種類・金額・日・営業日のずらし方・金種・費目・開始月・終了月） |
| `budgets` | 費目予算（月・費目・金額） |
| `rules` | お店→費目のルール（お店の名前の一部・費目） |
| `debts` | リボ・分割（名前・残高・時点・最低返済額・メモ） |
| `settings` | 安全残高・目標残高・給与の見込み・費目の一覧など |
| `review` | 要確認（種類・対象の明細・本文・解決したか） |

### 4.2 金種ごとの「予算から減る日」と「資産から減る日」

| 金種 | 予算から減る日 | 資産から減る日 | 入り方 |
| --- | --- | --- | --- |
| クレカ（三井） | 使った日 | 翌月26日（翌営業日） | メールから自動 |
| クレカ（セゾン） | 使った日 | 翌月4日（翌営業日） | 手入力か定期のお金（家賃） |
| 現金 | 使った日 | 使った日 | 手入力 |
| PayPayチャージ | チャージした日（チャージ額＝支出） | チャージした日 | 手入力 |
| 交通系チャージ | チャージした日（チャージ額＝支出） | カードでチャージ：翌月26日／現金でチャージ：その日 | カードでのチャージはメールから自動（モバイルSuicaは自動で「交通」） |

- **PayPay と交通系は、チャージしたときに使ったものとして数える**。チャージしたあと何に使ったかは管理しない。そのため PayPay や交通系の中に残っているお金は資産に数えない。
- **資産**は、口座と現金（財布）の合計で考える。ATM の引き出しは「移動」なので、使える額は変わらない（記録しなくてよい）。
- **ポイント払い**は扱わない（記録しない）。
- 金種（どこから払うか）とステータス（予定／速報／確定：どれくらい確かか）は別に持つ。クレカは明細の `card` でどのカードかを持つ（空なら1枚目のカード）。
- クレカの「返済」（リボ・分割）は、その日にそのカードの引き落としと一緒に出る。

### 4.3 取り込み（GAS）

15分ごとに、直近3日の `vpass.ne.jp` からのメールを**すべて**読む。
Gmail のラベルはスレッド単位でつくため、「読んだか」の判断には使わない。
`source_ref`（メールID＋何件目か）を DB で重複禁止にしているので、何度読んでも二重にならない。

| メール | 入れ方 |
| --- | --- |
| ご利用のお知らせ | 1件を `status=速報` で入れる（◇利用日・◇利用先・◇利用金額） |
| ご利用明細のお知らせ | 1通に入っている全件を `status=確定` で入れる |
| お支払い金額のお知らせ | `card_bills` に引落日と金額を入れる（同じ引落日なら上書き） |
| 読めなかったメール・取消や返品 | `review` に件名と本文の最初を入れる |
| それ以外（認証コードなど） | 何もしない |

- 費目は `rules`（お店の名前の一部→費目。いちばん長く一致したもの）で決める。合わなければ「未分類」にする。アプリを開いたときにも、まだ未分類の明細に今のルールを当て直す。
- アプリで費目を直すと、そのお店の名前でルールを自動で覚える（「Mastercard加盟店」のように中身が分からない名前は覚えない）。
- スクリプトプロパティ `SINCE` より前のメールは読まない（移行したデータと重ねないため）。
- 重複のまとめ（§6）は GAS ではせず、アプリを開いたときに計算エンジンが行う。

### 4.4 定期のお金

- `recurring` から、各月の給与（収入）・家賃など・通信やサブスクの予定を自動で作る（`status=予定`、今月から5か月先まで）。
- 日付が土日祝なら、設定に従って前か後ろの営業日にずらす（日本の祝日・振替休日に対応）。
- カード払いの定期のお金には「お店の名前のヒント」を入れられる（§6.2）。
- 給与と賞与は、設定の見込み額で予定を作る。入金があったら予定画面で「確定」にして金額を直す。

## 5. 計算式

### 5.1 今月の予算（自由に使えるお金）

```
今月の予算 T = 給与 ＋ 追加予算 − 固定費 − 目標用マイナス
```

| 予算の元 | 自動で出す値 | 手で直す |
| --- | --- | --- |
| 給与 | その月の収入のうち「給与」にしたもの（定期のお金から作った収入で扱いを決めていないものも給与とみなす） | できる |
| 追加予算 | その月の収入のうち「追加予算」にしたもの（イベチケなど） | できる |
| 固定費 | 大項目が固定費の費目（家賃・奨学金・保険・共済・通信・水道ガス光熱費・定期代・サブスク）の予算（見込み）の合計。予算を入れていない費目は、定期のお金のその月の額（定期のお金になければ、その月の明細と予定の合計） | 費目の予算で直す |
| 目標用マイナス | その月の「返済」（リボ・分割）の予定と引落 ＋ 毎月の貯金（設定の「貯金を始める月」から） | できる |

- 手で直した月はその値を使い、「自動に戻す」で明細と予定から出す値に戻せる。
- 賞与・売却代金・立替の返金などは、「追加予算」にしたときだけ入る（今までの家計簿と同じ）。
- 立替は自分の分だけを数える（金額 − 立替額）。返してもらうお金は収入に入れない。
- リボの返済は目標用マイナスの中で払う。そのため「返済」は予算の費目に入れない。
- 費目には大項目（固定費／変動費）がある。自由に使えるお金から使うのは変動費（予備を含む）だけ。

### 5.2 自由に使える残り

```
使った額 U = 今月の変動費の支出（速報・確定。金額 − 立替額。吸収されたものは除く）
予定 P    = 今月の変動費のまだ済んでいない予定
固定費の超過 = 固定費の各費目で、使った＋予定 が予算（見込み）をこえた分の合計
残り R    = T − U − P − 固定費の超過
```

- カードでも現金でも、使った分だけ減る。

### 5.3 費目ごと

```
予備の予算 = T − 予備以外の変動費の予算の合計
費目の残り = 予算 − 使った額 − 予定
1日に使える額 = floor(費目の残り ÷ 月末までの日数（今日を含む）)   … 残り ≤ 0 なら 0
```

- 費目予算は前の月から引き継ぐ。未分類は分類されるまで予備として数える。
- 予備がマイナスなら「費目に割り振りすぎ」と出す。

### 5.4 目標用マイナスの見通し

- 毎月の目標用マイナスと、予定に入っている賞与（予算に入れない収入のうち、内容に「賞与」とあるもの）を、まずリボ・分割の残り（予定のものも含む）の返済に回し、なくなったら貯金に回すとして、12か月分を出す。
- リボが0になる月と、貯金が目標残高に届く月を出す。利息・手数料は入れない。

### 5.5 口座の見通し（足りなくなる日の警告）

口座の残高からの計算は、いったん警告だけに使う（仕様は後で決める）。

```
A(t) = 最新の残高報告（口座＋現金）＋ 報告日より後〜t の収入 − 報告日より後〜t に口座から出る支出（§4.2 の日付）
```

- 同じ日のなかでは、収入を先に、支出をあとに数える。
- 資産が動く日が残高の報告日以前のもの（予定のままのものも含む）は、報告した残高に入っているものとして数えない。報告日より後で日付が過ぎた予定は、今日起きるものとして数える。
- カード請求額（`card_bills`）があるときは、そのカードのその引落日のクレカ支出は明細の合計ではなく請求額で数え、差があれば通帳の画面に出す。
- **今日〜今月分のカード引落日の前日に、A(t) が安全残高を下回る日があれば**、自由に使える残りのカードを赤にし、いくら足りないかと、先に入金が必要なことを出す。
- 目標②（引落日に足りない月）と「口座の見通し（通帳）」の画面も、この A(t) を使う。

### 5.6 計画をつくる

- 入れるもの：残したい額（目標）、今の貯金、賞与を回すか、毎月回す額。
- 各月に回す額 ＝ リボが残っている間は max(毎月回す額, その月のリボ返済の予定)、なくなったら毎月回す額。賞与を回すなら、その月の賞与も足す。
- 回した額はまずリボの残りに、なくなったら貯金に入れる。リボが0で貯金が目標以上になった月を「届く月」とする。最大36か月。
- 各月の自由に使えるお金 ＝ 給与（予定がなければ給与の見込み額）＋ 追加予算 − 固定費 − 回す額。
- 「達成したい月から」は、その月までに届く、いちばん少ない毎月回す額を1,000円単位で探す。
- 「この計画にする」で、今月から届く月まで（届かなければ24か月）の目標用マイナスを、回す額で上書きする。そのあとは同じ額を毎月の貯金として続ける。

### 5.7 引き落とし

その月に口座から出るお金を出す。

- 口座から直接：金種が「口座」の支出（予定を含む）。
- カードごと：引落日がその月になる締め月（`その月 − 引き落とす月数`）に、そのカードで使ったもの（返済を除く）＋ その月のそのカードの返済 ＝ **見込み**。
- そのカードとその引落日の請求額（`card_bills`。三井はメールから、ほかは手で入れる）があれば**確定**として請求額を使い、見込みとの差を出す。
- 合計引き落とし ＝ 口座から直接 ＋ カードごとの額。

### 5.8 来月の支払い予定

```
固定費（来月の固定費の見込み）＋ 変動費（来月の予算 T）＋ リボ・分割の返済（来月の「返済」）＝ 計
```

- 使う月で数える（予算の目線）。口座から出る日で見るのは §5.7。

## 6. 重複の処理

### 6.1 信頼度

```
予定 ＜ 手入力 ＜ カード速報 ＜ カード明細（確定）
```

新しい明細が入ったとき、それより信頼度の低い明細の中から相手を探す。見つかったら、信頼度の低いほうを吸収する（`merged_into` に吸収先を入れる。消さない）。

### 6.2 自動でまとめる条件

信頼度の低い明細から順に処理する（手入力→予定、速報→手入力、明細→速報、と段を上がるように吸収する）。
候補の中でいちばん信頼度の高いものが1件だけのとき、自動でまとめる。

| 相手 | 条件 |
| --- | --- |
| 実際の明細（手入力・速報） | 金種が同じ・金額が同じ・日付の差が3日以内 |
| 定期のお金の予定 | 日付の差が7日以内で、金額の差が20%以内（3,000円未満はぴったりのときだけ）。費目が同じか、どちらかが未分類 |
| 定期のお金の予定（ヒントつき） | 上に加えて、予定に「お店の名前のヒント」があり明細のお店にそれが入っていれば、費目が違ってもまとめる（定期代の Suica が「交通」で入るときなど） |
| 一回きりの予定（手で入れた予定など） | **自動ではまとめない**。上と同じ条件に合えば要確認に回し、「予定『○○』の支払いですか？」と聞く（同じ費目で似た金額の別の買い物と取り違えやすいため） |

まとめたときの値：

- 金額・日付・お店：信頼度の高い明細の値
- 費目：本人が入れた（直した）値、なければ予定の費目、なければルールの費目
- 買った物・メモ・立替額：空いていれば低いほうから引き継ぐ
- **カード速報→カード明細**：お店の名前が「Mastercard加盟店」でも、明細側の本当のお店の名前に置き換わる

### 6.3 要確認に回す

- 候補が2件以上ある
- 金額は同じだが日付の差が4〜7日
- 手入力の明細と、日付が近く金額が少し違う（10%以内）。メールの明細どうしで金額が違うものは別の買い物とする
- 一回きりの予定と、条件に合う明細（§6.2）

要確認の画面では「同じもの（まとめる）」か「どれとも別のもの」を選ぶ。「別のもの」にした組み合わせは、二度と候補に出さない。

### 6.4 そのほか

- まとめたあとでも、明細画面から「まとめを取り消す」ができる。
- クレカで手入力したのに7日たってもメールで入ってこない明細は、要確認に出す。

## 7. 作り方

- Vite＋React＋TypeScript、PWA（電波がなくても最後のデータを表示）。Supabase の設定がなければ「お試しモード」（データはその端末のブラウザの中）で動く
- 計算エンジン・重複処理・営業日の計算は、画面と分けた関数にして Vitest でテストする
- Supabase のテーブル定義は `supabase/migrations/` に置く。表はすべて `ggmg` スキーマに作る（`public` は使わない）
- GAS のコードは `gas/` に置く（clasp で上げるか、コピーして貼る）
- Vercel がビルドしてデプロイする。Supabase の URL と公開キーは Vercel の環境変数に入れる
- 今のアーティファクトのデータは、アプリで取り込める JSON に変えて渡す（家計のデータなのでリポジトリには入れない）。取り込みはアプリの「設定→データ」から、ログインした本人の権限で行う

- PayPay のチャージの自動取り込み（通知メールがないため、手で入れる）
