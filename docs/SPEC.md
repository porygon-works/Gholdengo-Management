# Gholdengo 家計簿 仕様書（v4）

前の家計簿アーティファクトを置き換える、独立した家計簿Webアプリ。
計算はすべてアプリの計算エンジン（`src/engine/`）で行い、Notion・Claude には依存しない。

v3 では、入出金を **口座明細** と **クレカ明細** の2つの表に分けた（v2 までは `entries` 1つ）。
v4 では、目標マスタを **計画**（返済・買い物・貯蓄）に置き換え、月ごとに予算を決められるようにした。画面は「ホーム・明細・見通し・計画・設定」の5つ。

---

## 1. 全体の作り

```
Gmail ──(15分ごと)── GAS ──→ Supabase ←──→ Webアプリ（Vercel・PWA）
  三井住友の通知メール        明細・予算・計画      計算エンジン・画面
```

| 部品 | 役目 |
| --- | --- |
| Webアプリ（Vercel） | 画面と計算。スマホのホーム画面に追加して使う |
| Supabase | 明細・予算・計画・設定を保存。プロジェクト porygon-works の `ggmg` スキーマに置く。メールでログインし、本人だけが読み書きできる（RLS） |
| GAS | 三井住友カードの通知メールを読み、クレカ明細と請求額を Supabase に書く |

---

## 2. 前提

| 項目 | 決定 |
| --- | --- |
| 月の区切り | 暦の月（1日〜月末） |
| 今月の予算 | その月に決めた額。決めていなければ目安（給与 ＋ 追加予算 − 固定費 − 計画の分）（§5.1） |
| カード | 三井：月末締め・翌月26日払い（ふだん使う・メールから入る）／セゾン：月末締め・翌月4日払い（家賃とリボ）。土日祝は翌営業日。カードごとに設定で変えられる |
| 給料日 | 15日（土日祝は翌営業日） |
| 銀行 | 入出金の通知メールはないので、口座明細は手入力か定期マスタから作る。ずれたら残高を直す |
| 安全残高 | 0円（設定で変えられる） |

## 3. データ

### 3.1 口座明細（`account_entries`）

口座と財布のお金の動き。**入れたらすぐ残高が変わる**（予定は計上日が来るまで変わらない）。

| 列 | 値 | 説明 |
| --- | --- | --- |
| `account` | 口座／財布 | どこのお金か。財布はあまり使わなくてよい |
| `direction` | 入金／出金 | |
| `status` | 予定／確定 | |
| `group`（大費目） | 出金：変動費／固定費／立替／クレカ支払い／その他<br>入金：給与／追加予算／立替の返金／その他 | 予算での扱いを決める（§5） |
| `category`（費目） | 食料品・奨学金など | 出金の変動費・固定費のときに使う |
| `name`（名称） | 奨学金・三井 10月分など | 一覧に出す名前 |
| `memo` | | |
| `date`（計上日） | | 口座（財布）が動く日 |
| `amount`（金額） | | いつもプラス |
| `source` | 手入力／定期／クレカ請求／目標（前の版）／計画／移行 | どこから作られたか |
| `source_ref` | | 同じものを2回作らないためのキー（定期：`rec:ID:月`、クレカ請求：`bill:カード:引落日`） |
| `recurring_id`・`goal_id` | | 作った元 |
| `plan_id`・`debt_id`・`plan_role`・`budget_month` | | 計画の取引（§3.4）。どの計画・どの残高の分か、支払い（`pay`）かまとめて払う（`lump`）か、どの月の予算を減らすか |
| `card` | | 大費目がクレカ支払いのとき、どのカードの請求か |
| `pair_id` | | ATM（口座→財布）のように2行で1つの動きのとき、相手の行 |
| `locked` | | 本人が直した。自動で作り直さない |

- **PayPayチャージ**：口座・出金・変動費（チャージした額を、その日に使ったものとして数える）
- **交通系を現金でチャージ**：財布・出金・変動費
- **ATMで引き出し**：口座・出金・その他 と 財布・入金・その他 の2行（`pair_id` でつなぐ）。予算は動かない
- **予定は計上日が来たら自動で確定**にする（定期・クレカ請求・計画から作ったもの）。手で入れた予定は、本人が確定にする
- 予定のまま計上日を過ぎた手入力の予定は、「日付が過ぎた予定」として出す（口座の今後の動きでは今日に数える）

### 3.2 クレカ明細（`card_entries`）

カードで使ったもの。**使っても口座はすぐには減らない**。予算が減り、来月の支払い予定（クレカ支払いの予定）が増える。

| 列 | 値 | 説明 |
| --- | --- | --- |
| `card` | 三井／セゾン | どのカードか（どの請求に入るか） |
| `status` | 予定／確定 | メールの速報も、実際に使ったものなので確定 |
| `date`（利用日） | | 締め日と合わせて、どの月の請求に入るかが決まる |
| `amount`（金額） | | |
| `group`（大費目） | 変動費／固定費／立替／分割 | §3.2.1 |
| `category`（費目） | 食料品など | 変動費・固定費のとき |
| `name`（名称） | 商品名など | |
| `shop`（店） | 利用した店名 | メールから入る。ルールで費目を決めるのに使う |
| `tatekae` | | 一部だけ立て替えたときの、立替の額（自分の分 ＝ 金額 − 立替額） |
| `source` | 手入力／カード速報／カード明細／定期／目標／移行 | |
| `source_ref`・`merged_into`・`not_dup`・`locked`・`recurring_id`・`goal_id` | | 重複の処理（§6）と、作った元 |

#### 3.2.1 大費目ごとの扱い

| 大費目 | 予算 | 請求（口座から出る額） |
| --- | --- | --- |
| 変動費 | 自分の分を数える | 入る |
| 固定費 | 固定費の見込みと比べる（§5.1） | 入る |
| 立替 | 数えない（全額が立替） | 入る。返してもらう分は口座明細の「入金・立替の返金」の予定として作れる |
| 分割（返済） | 数えない | 入る。前の版で目標マスタから作った毎月の返済額（v4 では計画の支払いを口座明細に作る） |
| 分割（購入） | 数えない | 入らない。リボ・分割で買った物。返済の計画の残高に足す |

### 3.2.2 明細を消す

- メールや定期・目標から作った明細（`source_ref` がある）は、行を残して `deleted` にする。計算にも画面にも出さない。こうしないと、メールの取り込み（直近3日を読み直す）や予定づくりで、また同じものが作られる。
- 手で入れた明細は行ごと消す。
- クレカ明細を消すと、その明細にまとめた明細（速報・手入力・予定）も一緒に消す。ATM の口座明細は相手の行も消す。

### 3.3 クレカの請求 → 口座明細

- カードごと・引落日ごとに、口座明細に「出金・**クレカ支払い**・予定」の行を自動で作る（名称「三井 10月分」）。
  - 予定のあいだは、金額 ＝ そのカードのその締め期間のクレカ明細（予定を含む。分割（購入）を除く）の合計。カードで使うたびに増える。
  - 確定の額が届いたら**確定**にする。三井はメール（お支払い金額のお知らせ）から自動で、セゾンや本人の報告は手で入れる。明細の合計との差を出す。
  - 引落日が来て確定の額がまだなければ、**見込みの額で確定**して口座から引く。あとから請求額が届いたら上書きする。
- クレカ支払いの行は予算に数えない（中身はクレカ明細で数えている）。

### 3.4 計画（`plans`・`plan_debts`・`plan_funds`）

計画は「ためて、まとめて使う」ための入れ物。種類は3つ。

| 種類 | 使う日 | 使う額 | 例 |
| --- | --- | --- | --- |
| 返済 | まとめて返す日 | 残高 − まとめて返す日より前の支払い | リボを賞与で全額返す |
| 買い物 | 使う日 | 金額（`target`） | 新しいPC |
| 貯蓄 | なし | 目標額（`target`） | 給料1か月分 |

計画は次の3つを持つ。

| もの | 表 | 中身 |
| --- | --- | --- |
| 残高（返済だけ） | `plan_debts` | 支払先ごとの残高と、見た日（`as_of`）。カードのサイトで見た額に直す。直すと見た日は今日になる |
| 計画の取引 | `account_entries`（`plan_id`） | **支払い**（`plan_role = pay`）：リボの毎月の支払いなど、口座から出るお金。予定で作り、額が分かったら直して確定にする。`budget_month` の月の予算から引く。カードの請求と一緒に引き落とされるものは `card` にそのカードを入れる<br>**まとめて払う**（`plan_role = lump`）：使う日に1行。額はアプリが残高から出し（買い物は金額）、予定のあいだは開くたびに合わせる |
| 確保額に入れる分 | `plan_funds` | 口座のお金は動かさず、口座に残しておく分。予算から（`budget`：`budget_month` の月の予算を減らし、その月のカードの引落日に確保額に入る）・賞与から（`bonus`）・予備から（`spare`） |

- まとめて返す額 ＝ Σ（残高 − 見た日のあと、まとめて返す日より前の、その残高の支払い）。
- 計画の確保額（その日）＝ その日までに入った「確保額に入れる分」の合計。使う日からは0（まとめて払う行で口座から出る）。貯蓄は目標額まで。
- そろい具合：使う日の前の日までにたまる額が使う額に足りなければ、足りない分をその日の予備（§5.5）でまかなえるかを出す。
- カード会社の請求額（確定の額）には、そのカードと一緒に引き落とされる計画の支払いが入っている。二重に数えないよう、クレカ支払いの行の額はそれを引いた額にする（画面の請求額の欄は、引く前の額）。
- 名前（計画・残高の先・取引）はどれも画面で直せる。計画の取引は明細にもそのまま出る（同じ1行）。
- 計画を消すと、予定のままの計画の取引も消える。確定した取引は残る（つながりだけ外れる）。終わった計画は「終わった」にして一覧の下に回す。

**前の版の目標マスタ（`goals`）から写す**：動いている目標があれば、開いたときに1回だけ計画に写し、目標は止める。

- 返済の目標は、臨時の返済の日（今日から先のいちばん近い日）が同じものを1つの計画にまとめる（その日がまとめて返す日）。残高は今日の見込み（入れた日のあとに来た毎月の返済を引く）。
- 毎月の返済（6か月分・まとめて返す日より前）は計画の支払いにする。カードの目標ならそのカードの引落日に、カードの請求と一緒に出る支払いにする。
- 積立の目標は貯蓄の計画にして、毎月の額は「予算から」確保額に入れる分にする。もうたまっている額は「予備から」の確定の分にする。
- 目標から作った予定（まだ予定のもの）は消す。

### 3.5 予算マスタ（`budgets`）

| 列 | 説明 |
| --- | --- |
| `month` | どの月の予算か |
| `category` | 費目（`#` で始まる行は前の版の名残で、使わない） |
| `amount` | 予算額 |

- ヘッダーの月を来月にすれば、来月の予算を見て直せる。
- 予算を入れていない月は、前の月の額を引き継ぐ（その月になったら、引き継いだ額をその月の分として保存する）。
- 予算の決め方：基本は前の月を引き継いでアプリで直す。Claude と相談して決めた額は、JSON にして「設定→データ」から取り込む。

### 3.5.1 月の予算（`months`）

| 列 | 説明 |
| --- | --- |
| `month` | どの月か |
| `budget` | その月に決めた予算。空なら目安（§5.1）をそのまま使う |

## 4. 画面

### 4.1 共通

- 金額は頭に ¥ をつけて右寄せ。入力の欄も同じ。使った額と予定の額は、別の列（表でないところは「使った ¥…・予定 ¥…」）に分けて出す。
- 払い方の選択肢は「クレカ（三井）・クレカ（セゾン）・現金・PayPay・口座」。
- ヘッダー：画面の名前・表示している月（‹ ›。ホーム・明細・設定）・メニュー（口座と財布・要確認・読み直す・ログアウト）
- フッター：ホーム・明細・見通し・計画・設定
- 説明の文は短くする（グレーの文を増やさない）。

### 4.2 ホーム（ダッシュボード）

1. **今月の予算**と**残り予算**。今月の予算をタップすると設定の予算へ
2. **費目ごと**：変動費の費目ごとに「使った（予定を含む）／予算」とバー。最後に固定費の合計。タップでその費目の明細
3. **使ったものを入れる**：費目・金額・払い方
4. **口座**：口座残高（タップで直す）・実質残高・次の給料日前日の見込みと、小さいグラフ（タップで見通しへ）
5. **近い予定**：これからの口座の動きを5件（タップで明細か計画）
6. **計画**：計画ごとの「たまる額／使う額」（タップで計画の中身）

### 4.3 明細

- 費目ごと／日付ごと／予定（月ごとの予定と、日付が過ぎた手入力の予定）
- タップで詳細・編集・削除

### 4.4 見通し（口座の見通し）

1. 線グラフ（§5.5）：口座残高・実質残高・両方を切り替え。長さは1か月・3か月・全部、‹ › で動かす。なぞると縦の線が動き、その日の口座残高・実質残高・計画ごとの確保額・その日の動きが出る。今日の線と、給料日前日の点（○）
2. 給料日前日の残高（確保額）と、前の月からの増減。「確保額の増減」を開くと、まとまり（給与・固定費／カード／計画／臨時の入出金）ごとの動き
3. これからの入出金：月ごとに区切って、日・内容・入出金・残高（タップで明細か計画）

### 4.5 計画

1. 計画の一覧：計画・使う日・使う額・たまる額（そろう／残りは予備から／足りない）。その下に次の取引を1行
2. 確保額の内訳：給料日前日ごとに、確保額・返済用・買い物用・貯蓄・予備
3. 計画の中身（タップで開く）：名前・使う日・使う額・たまる額。返済は残高の表（先・残高・まとめて返す額）。予定の取引（日・内容・金額・予定／確定・消す）と、最後にまとめて払う行。支払い・予算から・賞与から・予備からを足せる
4. 計画を足す：種類・名前・金額（返済は残高）・使う日・毎月の額・始める月・何か月分・払い方（返済）・賞与から

### 4.6 設定

- **予算**：予算の出し方（給与 ＋ 追加予算 − 固定費 − 計画の分 ＝ 目安）と、その月の予算の入力（空なら目安）。費目ごとの予算（固定費・変動費。予備は残りが自動で入る）
- **区分**：費目の名前の変更（明細・予算・ルール・定期・設定の一覧に入っている費目も一緒に変える）、大費目（変動費／固定費）の切り替え、1日に使える額を出すか、費目の追加・削除。大費目の名前の変更
- **口座とカード**：給料日・安全残高・給与の見込み額・カード（名前・締め日・引落日・引き落とす月、カードの追加）
- 給与・賞与・定期マスタ・お店のルール・データ
- 口座と財布（メニュー）：残高を直す・ATM・直した履歴

## 5. 計算式

### 5.1 今月の予算

```
目安       = 給与 ＋ 追加予算 − 固定費 − 計画の分
今月の予算 T = その月に決めた予算（months.budget）、なければ目安
```

| 予算の元 | 出し方 | 直し方 |
| --- | --- | --- |
| 給与 | その月の口座明細の入金のうち、大費目が給与のもの（予定を含む） | 口座明細を直す |
| 追加予算 | その月の口座明細の入金のうち、大費目が追加予算のもの（予定を含む） | 口座明細を直す |
| 固定費 | 予算マスタにある固定費の費目の合計（見込み）。予算がない費目は、その月の定期マスタの額、それもなければその月の固定費の明細の合計 | 予算マスタ |
| 計画の分 | その月の予算を減らす計画の支払い（`budget_month` がその月）＋ 予算から確保額に入れる分（§3.4） | 計画の中身 |

- 決めた予算が目安より少なければ、その分は口座に残って確保額の予備になる。予算をこえて使えば、その分だけ確保額が減る。

### 5.2 残り予算

```
変動費で使った額 U ＝ その月のクレカ明細の変動費（自分の分）＋ その月の口座明細の変動費の出金（口座・財布）   … 確定
変動費の予定 P    ＝ 同じものの予定
固定費の超過      ＝ 固定費の費目ごとに、使った＋予定（クレカ明細・口座明細）が見込みをこえた分の合計
残り予算 R        ＝ T − U − P − 固定費の超過
```

- 費目ごとの予算・残り・1日に使える額は v2 と同じ（予備 ＝ T − 予備以外の変動費の予算の合計。未分類は予備で数える）。

### 5.3 クレカの請求の額

```
見込み（カード c・引落日 d）＝ 締め期間（d の月 − 引き落とす月数 の1日〜締め日）の c のクレカ明細の金額の合計
                               （予定を含む。分割（購入）を除く。立替もそのまま入る）
請求額 ＝ 確定していれば確定の額、なければ見込み
```

### 5.4 いまの口座残高

```
いまの口座残高 ＝ 最後に入れた（直した）口座の残高 ＋ そのあと今日までの口座明細（口座）の 確定 の 入金 − 出金
```

- 財布も同じように数える。
- 残高を直すと、アプリの計算との差を記録に残す。

### 5.5 口座の見通し

```
過ぎた日の口座残高 ＝ いまの口座残高 − その日のあと今日までの、確定した口座明細（口座）
これからの口座残高 ＝ いまの口座残高 ± 明日〜その日の、口座明細（口座）の予定と確定
                     （クレカ支払いの見込み・計画の支払い・まとめて払う行を含む）
                     ＋ これからカードで使う見込み（その月の残り予算を、その月のカードの引落日に）
実質残高           ＝ 口座残高 − まだ引き落とされていないカードの分
                     （使った日に増え、引落日に減る。これから使う見込みは月の中で日割り）
確保額             ＝ 給料日の前日の口座残高
確保額の内訳       ＝ 計画ごとの確保額（§3.4）と、予備（確保額 − 計画の確保額の合計）
```

- 前の月の1日から、6か月先の月末まで。
- 予定のまま計上日を過ぎた手入力の予定は、今日に数える。
- 実質残高にはリボの残高は入れない（返済の計画の残高で見る）。

### 5.6 来月の支払い予定

来月に口座から出るお金を、大費目ごとの表で出す（行をタップすると、その大費目の明細の一覧を子画面で開く。明細をタップすると詳細）。

| 大費目 | 中身 |
| --- | --- |
| 固定費 | 来月の請求に入るクレカ明細の固定費（自分の分）＋ 来月の口座明細（口座）の固定費の出金 |
| 変動費 | 同じく変動費 |
| 計画の支払い | クレカ明細の分割（返済）＋ 計画の支払い（口座の出金） |
| 立替 | クレカ明細の立替 ＋ 一部だけ立て替えた分 ＋ 口座の立替の出金 |
| その他 | 口座のその他の出金 |
| クレカの確定の額との差 | 請求額が確定していて、明細の合計と違うとき |
| 計 | 来月に口座から出るお金の合計 |

- 「来月の請求に入るクレカ明細」は、来月に引き落とされる締め期間のもの（三井・セゾンとも月末締め・翌月払いなので、今月使ったもの。予定を含む）。
- 口座明細のクレカ支払いの行は数えない（中身のクレカ明細で数えている）。

## 6. 重複の処理（クレカ明細）

### 6.1 信頼度

```
予定 ＜ 手入力 ＜ カード速報 ＜ カード明細
```

新しい明細が入ったとき、それより信頼度の低い明細の中から相手を探す。見つかったら、信頼度の低いほうを吸収する（`merged_into` に吸収先を入れる。消さない）。

### 6.2 自動でまとめる条件

信頼度の低い明細から順に処理する（手入力→予定、速報→手入力、明細→速報、と段を上がるように吸収する）。
候補の中でいちばん信頼度の高いものが1件だけのとき、自動でまとめる。

| 相手 | 条件 |
| --- | --- |
| 実際の明細（手入力・速報） | 金種が同じ・金額が同じ・日付の差が3日以内 |
| 定期のお金の予定 | 日付の差が7日以内で、金額の差が20%以内（3,000円未満はぴったりのときだけ）。費目が同じか、どちらかが未分類 |
| 定期のお金の予定（ヒントつき） | 上に加えて、予定に「お店の名前のヒント」があり明細のお店にそれが入っていれば、費目が違ってもまとめる（定期代の Suica が「交通」で入るときなど） |
| 一回きりの予定（手で入れた予定など） | **自動ではまとめない**。上と同じ条件に合えば要確認に回し、「予定『○○』の支払いですか？」と聞く（同じ費目で似た金額の別の買い物と取り違えやすいため） |

まとめたときの値：

- 金額・日付・お店：信頼度の高い明細の値
- 費目：本人が入れた（直した）値、なければ予定の費目、なければルールの費目
- 買った物・メモ・立替額：空いていれば低いほうから引き継ぐ
- **カード速報→カード明細**：お店の名前が「Mastercard加盟店」でも、明細側の本当のお店の名前に置き換わる

### 6.3 要確認に回す

- 候補が2件以上ある
- 金額は同じだが日付の差が4〜7日
- 手入力の明細と、日付が近く金額が少し違う（10%以内）。メールの明細どうしで金額が違うものは別の買い物とする
- 一回きりの予定と、条件に合う明細（§6.2）

要確認の画面では「同じもの（まとめる）」か「どれとも別のもの」を選ぶ。「別のもの」にした組み合わせは、二度と候補に出さない。

### 6.4 そのほか

- まとめたあとでも、明細画面から「まとめを取り消す」ができる。
- クレカで手入力したのに7日たってもメールで入ってこない明細は、要確認に出す。

## 7. 作り方

- Vite＋React＋TypeScript、PWA（電波がなくても最後のデータを表示）。Supabase の設定がなければ「お試しモード」（データはその端末のブラウザの中）で動く
- 計算エンジン・重複処理・営業日の計算は、画面と分けた関数にして Vitest でテストする
- Supabase のテーブル定義は `supabase/migrations/` に置く。表はすべて `ggmg` スキーマに作る（`public` は使わない）
- GAS のコードは `gas/` に置く（clasp で上げるか、コピーして貼る）
- Vercel がビルドしてデプロイする。Supabase の URL と公開キーは Vercel の環境変数に入れる
- 今のアーティファクトのデータは、アプリで取り込める JSON に変えて渡す（家計のデータなのでリポジトリには入れない）。取り込みはアプリの「設定→データ」から、ログインした本人の権限で行う

## 8. この版でやらないこと

- PayPay のチャージの自動取り込み（通知メールがないため、手で入れる）
